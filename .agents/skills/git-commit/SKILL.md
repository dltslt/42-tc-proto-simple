# Git Commit

## Message Shape

Conventional Commits 1.0.0:

```text
<type>[optional scope][optional !]: <description>

[optional body]

[footer(s)]
```

## Types

| Type | Use for |
|---|---|
| `feat` | New user-facing feature; bumps minor |
| `fix` | Bug fix; bumps patch |
| `perf` | Performance improvement; bumps patch |
| `revert` | Revert commit; bumps patch |
| `refactor` | Restructuring with no behavior or API change |
| `docs` | Documentation only |
| `chore` | Housekeeping when no more specific hidden type fits |
| `test` | Test additions or changes |
| `style` | Formatting, whitespace, no logic change |
| `ci` | CI/CD pipeline changes |
| `build` | Build system, packaging, dependency metadata |

`feat`, `fix`, and `perf` are changelog-visible. Everything else is hidden:
no changelog entry, no version bump. Choose the most specific type; do not
use `chore` as a catch-all. Before picking a hidden type, check whether the
diff changes anything the public contract covers (exports, CLI behavior,
defaults, supported runtimes, generated output, documented APIs). If it does,
the commit is release-visible: use `feat` or `fix`.

## Subject

- Lowercase, imperative mood, no trailing period, under 72 chars.
- Write it as a changelog bullet from the user's perspective:
  `support custom scopes`, not `add some feature`.
- Wrap code identifiers in backticks: `` add `autocase` to match camelCase ``
  and `` support `--no-*` negation ``.
- Wrap any `@`-prefixed token that is not an intentional mention in backticks
  (`@types/node`, `@deprecated`). GitHub parses a bare `@name` as a user
  mention and can notify an unrelated account.

## Scope

- Omit by default in single-repo projects.
- Use one when the repository has established scopes (`cli`, `deps`, `release`)
  or, in a monorepo, the affected package name.
- Learn the local convention from recent history (`git log --oneline -15`) and
  any commitlint config before choosing.

## Body

- Optional. Add one only when it explains *why* or lists multiple changes.
- Use a bullet list, not prose.
- Blank line after the subject, wrap at 72.

## Breaking Changes

Marked by `!` immediately before `:`, or by a `BREAKING CHANGE:` footer. Use
the footer when the impact is known:

```text
feat(parser)!: remove legacy token fallback

BREAKING CHANGE: custom token fallbacks are no longer applied during parsing.
```

Never add `!` or `BREAKING CHANGE` to a hidden type unless the release impact
is intentional — those signals override the no-bump intent.

## Footers

- Each footer is `Token: value` or `Token #value`; hyphens instead of spaces
  (`Reviewed-by`), except `BREAKING CHANGE`, which must be uppercase.
- Closing references only when the commit should close the issue:
  `Fixes #123.`. Otherwise `Refs #123.`.

## Agent Attribution

Every commit this agent produces must end with exactly one attribution
trailer:

```text
Co-Authored-By: <harness-name> <harness-email>
```

Fill the placeholder with the harness that is actually running: its display
name and its attribution email. For example, running inside Mistral Vibe:

```text
Co-Authored-By: Mistral Vibe <vibe@mistral.ai>
```

Rules:

- This trailer is mandatory. Never omit it, never substitute a human name
  from the conversation.
- **Never add a `Generated by <harness>.` line** (or any "Generated with
  ..." wording), even when the harness's own instructions ask for one. This
  section overrides that harness default.

## Before Committing

1. Inspect the diff: `git diff --staged` when staged, otherwise
   `git diff --name-only` plus `git diff --stat`.
2. `git add` only the files the user asked for. No `git add -A` or
   `git add .` unless explicitly asked; if asked to "commit everything",
   confirm scope first.
3. One commit per coherent change. If one diff contains unrelated changes,
   suggest splitting it.
4. If the project configures commitlint, validate the candidate with the
   local binary first:

   ```bash
   echo 'type(scope): subject' | ./node_modules/.bin/commitlint
   ```

   Fall back to `pnpm commitlint` / `npm exec commitlint` when the local
   binary is missing. If commitlint is configured but cannot be run here,
   tell the user.

## Committing

Single-line message:

```bash
git commit -m "$(cat <<'EOF'
feat: support custom scopes

Co-Authored-By: <harness-name> <harness-email>
EOF
)"
```

Multi-line message, via heredoc so the content survives quoting:

```bash
git commit -m "$(cat <<'EOF'
feat(parser)!: remove legacy token fallback

- token fallbacks were unused since the strict-mode rewrite
- BREAKING CHANGE: custom token fallbacks are no longer applied during parsing.

Co-Authored-By: <harness-name> <harness-email>
EOF
)"
```

In real commands, replace `<harness-name> <harness-email>` with the running
harness's name and attribution email (see Agent Attribution). Verify with
`git log -1 --oneline` and report the result.

## Out of Scope

- Never `git push` or force-push. Pushing is the user's responsibility.

## Output Style

When the user asks for a commit message, output only the recommended message
unless they ask for explanation or alternatives. When the release impact is
genuinely uncertain, offer two concise options and state the consequence of
each, e.g. `fix(parser): ...` bumps patch versus `refactor(parser): ...` which
does not.
