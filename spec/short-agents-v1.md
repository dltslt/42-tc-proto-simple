# Lerch — product context for prototypes

Condensed from `spec/product-v7.md` (discussion draft, 30 Oct 2026). For agents building vertical or exploratory prototypes. Where this file and the spec differ, the spec wins. This file holds product context only. The task prompt supplies the stack, the prototype's scope, and its success test.

## The product in brief

Lerch is a task and project management app, built for a team first. It is a hub for the next relevant piece of work: it stays out of the way and keeps every ordinary change to the fewest steps. The core is agnostic (items, their relations, a space). Views, templates, and actions are shipped defaults that a team can change or leave. The range runs from a shopping list to a multi-team engineering organisation. Single-person use is another combination of the same parts.

## Principles

1. **Minimum steps.** Create or update in as few steps as possible, ideally one gesture (a swipe on a phone).
2. **Level and scope decide the fields.** Show only the fields that belong to the current level and scope. A value entered in one place is there in all the others.
3. **Passive communication.** Setting a state or a blocker is itself the message to the team. No separate notify step.
4. **Links, not copies.** Artifacts are titled links to documents that live elsewhere.
5. **Widgets on a grid.** A space's interface is built from widgets. A use takes up each one or leaves it.

## Status tags

- **SETTLED**: stated as a 29 Oct session outcome in the spec.
- **PROPOSED**: in the spec as a proposal, not yet confirmed by the team (includes the 30 Oct changes).
- **OPEN**: the spec has no answer. Assume nothing and stub it (see the working rules).
- **LATER**: final-product feature or option. Do not build unless the prompt asks.

## Domain model

**Item** is the generic object. A **task** is a record of an item and the everyday name for it. Epic, story, task, subtask, and project are items at different levels, joined by parent and child. A project is an item, not a space. [SETTLED]

**Task fields** [PROPOSED]

| Field | Notes |
|---|---|
| title | the only field needed to create an item |
| contributors | a person or an agent. One may hold the lead |
| tags | markers that connect items. May be autogenerated |
| state | `unstarted`, `started`, or `done`. It is the category of the item's kanban column |
| kanban | the one column the item sits in. Defaults: `backlog` (unstarted), `in progress` (started), `done` (done). A team adds columns, and several may count as `started` |
| effort | how much time the item would take |
| scheduled time | a time slot. A person's availability is not this field |
| description | a longer explanation |
| correlation | links to other items |

**Their own records** [SETTLED unless noted]

| Record | What it is |
|---|---|
| parent and child | the hierarchy is a relation record between items, not a fixed schema |
| artifact | `id`, `title` (required), `url or path`. Never a copy of the document. A task shows its artifacts, and an artifact leads back to its tasks |
| event | a log of actions on a task. May be autogenerated. Its fields are not specified |
| blocker (link) | joins two items, may cross projects. Carries a severity (see below) [PROPOSED storage] |

**Space** [PROPOSED]: the identity of an organisational context. A person alone is a context. Every user has a space and can also join an organisation's space. A space holds resources (tasks and other records), members (including an administrator), policies (what a person can see and do, and what is editable by whom), and configurations (the interface built there). The policies are the security boundary. The space is billable. A view can filter by space, but the filter is not the space.

**Actors**: a person, or an agent. An agent can be a contributor on an item.

**Two scales and one score, not to be mixed up** [SETTLED]

- Item score: doesn't work, bare minimum, satisfactory, excellent.
- Blocker severity: I cannot do anything, I will be stuck, I can proceed but slowed down, just nice to have. Severity is triaged on a blockers dashboard.
- Experience points are a separate user feature (an option for the school subject).

## Behaviours to build against

- Moving an item to a column needs no approval by default. [PROPOSED]
- A review is not a state or a column. It is a new task asking someone to review something else. [SETTLED]
- Setting a blocker tells the team. A task that affects other tasks shows up in their definition of ready. [PROPOSED]
- A calendar clash prompts a reschedule. More work than the available time prompts setting priorities. [PROPOSED]
- Typing a link collects it, and Lerch then offers to make it an artifact or makes one automatically (which one is OPEN).
- "Cut the bread" example from the notes: dinner has a task "cut the bread", and "buy cutlery" has a task "bread knife". The bread knife blocks cutting the bread.

## Open decisions and safe defaults

| Open question (medal) | Default for a prototype |
|---|---|
| What makes work the next relevant thing to show? (gold) | no product rule exists. Any ordering is an experiment, so say which one you used |
| Does a task sit in exactly one space? (gold) | one `space` per task. No cross-space features |
| What do policies allow? (gold) | one allow-all policy behind a single function |
| Which candidates are objects of their own? (gold) | actors, tags, and blockers as simple records. Do not model views, templates, meetings, or journals |
| Which content connections belong? (gold) | explicit parent and child, plus tags. No similarity or embeddings unless the prompt is about them |
| Blocker, dependency, clash: one feature? (gold) | one blocker link. No clash detection |
| Web, desktop, mobile, or a mix? (gold) | the prompt states the platform |
| What do you open every morning? (gold) | not named. A prototype may explore it |
| Agent: contributor, API client, or both? (gold) | an actor of kind person or agent. Agent authentication is open |
| What is the smallest version? (gold) | the prompt defines the slice |

## Working rules for prototype agents

1. Build thin and vertical: interface, server, and storage for one scenario at a time.
2. Do not invent product behaviour. For OPEN items, use the simplest stub and keep it in one named place (a config value or one module), so an answer can replace it.
3. Use the spec's names: item, task, state, kanban column, artifact, event, blocker, space.
4. Never store a copy of a document. An artifact is a title and a link.
5. Keep user features (comments, availability, messages, experience points) separable from product features. The school subject lists them apart.
6. Exploration is welcome. In your final message, name the open question the prototype touched, what it showed, and every field or assumption you added.
